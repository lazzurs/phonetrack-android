# Releasing

Releases are fully automatic: **merging a pull request with a user-facing change publishes a
release** ([`.github/workflows/release.yml`](.github/workflows/release.yml)). The version, the release
notes and [`CHANGELOG.md`](CHANGELOG.md) are all **derived from the commit messages**; nobody writes
them by hand, and nothing needs to be run or approved.

Each release gets:

- **notes**: an optional hand-written introduction from
  `.github/release-highlights/<version>.md`, then the changes since the previous release,
  generated by [git-cliff](https://git-cliff.org) ([`cliff.toml`](cliff.toml)) and grouped into
  Security, Features, Fixes, Changes, Build and CI, Documentation, each linking to its commit;
- the **signed APKs** `phonetrack-<version>-normal.apk` and `phonetrack-<version>-play.apk`;
- the **R8 mapping files** `phonetrack-<version>-<flavor>-mapping.txt`, to decode obfuscated
  stack traces with `retrace`;
- **`SHA256SUMS.txt`** for all of the above;
- for a full release, the same notes **added to `CHANGELOG.md` on `main`**, in the release commit.

## Commit messages

The changelog is only as good as the commit messages, so they follow
[Conventional Commits](https://www.conventionalcommits.org): `type(scope): description`, written
for someone reading the release notes. CI rejects a pull request whose commits don't
(`scripts/release/check-commits.sh`).

| Type | Section in the notes | Publishes a release |
|---|---|---|
| `fix(security):` (any type with the `security` scope) | Security | yes |
| `feat:` | Features | yes |
| `fix:` | Fixes | yes |
| `refactor:`, `perf:` | Changes | yes |
| `build:`, `ci:`, `chore:` | Build and CI | no, listed in the next release |
| `docs:` | Documentation | no, listed in the next release |
| `test:`, `style:` | not listed | no |

A breaking change (`type!:` or a `BREAKING CHANGE:` footer) always publishes a release. A dependency
update that fixes a vulnerability is `fix(security):` (or `build(security):`), not `build(deps):`, so
that it's released right away.

Pull requests are merged with a merge commit, so each commit shows up in the notes. Merge
commits themselves are left out.

## Versions and tags

- Plain [SemVer](https://semver.org) tags: `vX.Y.Z` is a full release (marked *latest*),
  `vX.Y.Z-suffix` (e.g. `v0.3.0-rc.1`) is a pre-release. A release's notes cover everything since
  the previous *full* release; pre-releases don't update `CHANGELOG.md`.
- The version lives in one place, [`gradle.properties`](gradle.properties):
  - `appVersionName` must equal the tag without the `v`;
  - `appVersionCode` must be **higher than the previous release's**. Android refuses to install
    a lower or equal version code as an update.
- The next version is computed from the commits since the previous release
  (`git-cliff --bumped-version`, `[bump]` in [`cliff.toml`](cliff.toml)): a breaking change
  (`type!:` or a `BREAKING CHANGE:` footer) bumps the major version, `feat:` the minor, anything else
  the patch. While the version is `0.x`, a breaking change bumps the minor instead. `appVersionCode`
  goes up by one.
- Nobody edits the version by hand, normally: the release workflow commits it. To choose a version
  (e.g. `1.0.0`), a maintainer sets `appVersionName` (and a higher `appVersionCode`) in a pull
  request; when that is merged, the workflow releases that version instead of computing one. So pull
  requests from other repositories can't change the version (CI fails them,
  `scripts/release/check-version-unchanged.sh`).

## Supported Android versions

`minSdk` (in [`app/build.gradle.kts`](app/build.gradle.kts)) is the **oldest Android version that
still gets security updates**, i.e. the oldest one in the "Updated AOSP versions" of the latest
[Android Security Bulletin](https://source.android.com/docs/security/bulletin). Older versions
are dropped, unless that would break a critical feature. Check it at each release.

- 2026-09: the bulletin covers Android 14, 15, 16 and 17 → `minSdk 34` (Android 14).
- `targetSdk` is the newest Android version (currently 37, Android 17).

## How a release happens

On every push to `main` (a merged pull request), the Release workflow:

1. decides: if `gradle.properties` has a version without a tag, that version; else, if there are
   user-facing commits since the previous release (`scripts/release/releasable.sh`), the next version
   from `git-cliff --bumped-version`; else nothing, and it stops;
2. builds the APKs with that version, after the unit tests, signs them with the release key and
   checks that they really are signed with it (see [Signing](#signing));
3. commits `build: release X.Y.Z` on top of the merge (the version in `gradle.properties` and the
   `CHANGELOG.md` entry), tags it `vX.Y.Z` and pushes both at once, then publishes the GitHub release.

If `main` moved on during the run, nothing is pushed: the run for the newer push releases everything.

**Highlights** (optional): a short hand-written introduction above the generated notes, for what users
**have to do** after updating. Add `.github/release-highlights/next.md` in the pull request; the
release renames it to `X.Y.Z.md`.

**Testing a release build first**: *Actions → Release → Run workflow* (on `main` or a branch) is a
dry run of what a push would release. Its artifact has the APKs (optimized by R8, unlike debug
builds) and the notes. Only a dry run **on `main`** is signed with the release key
(`release-dry-run-X.Y.Z`). On any other branch the code hasn't been reviewed, so the APKs are
debug-signed and named so (`release-dry-run-X.Y.Z-debug-signed`,
`phonetrack-X.Y.Z-normal-debug-signed.apk`): they can't be installed as an update of a released
app, only next to nothing (uninstall first, or use another device or user profile).

**Tags must be on `main`**: the workflow refuses a `v*` tag whose commit is not on `main`, before
anything is built or signed. A release is code that was merged, never a branch.

**Pre-release**: push a tag `vX.Y.Z-rc.N` on a commit of `main` whose `gradle.properties` has the
version `X.Y.Z` and that isn't released yet. Pre-releases don't update `CHANGELOG.md`. Since a merge
to `main` is released right away, there is rarely such a commit: in practice a pre-release is only
possible while the automatic release is not working.

**Tag by hand** (e.g. if the workflow is broken): push a `vX.Y.Z` tag on a commit of `main` whose
`gradle.properties` has that version; the workflow checks and publishes it.

To preview locally: `pipx install git-cliff`, then `scripts/release/releasable.sh`,
`scripts/release/bump.sh` (sets the next version) and `scripts/release/prepare.sh` (writes
`release-out/RELEASE_NOTES.md` and `release-out/CHANGELOG_ENTRY.md`).

## Open source safety

Merging a pull request publishes a release to users, signed with the fork's key, so **review a pull
request as if it were the release**: the merge is the only approval. Only people with write access
can merge or push. Nothing that handles the signing key or pushes to the
repository runs for pull requests: `build.yml` runs on `pull_request` (read-only token, no secrets
for forks), and there is no `pull_request_target` workflow. Keep it that way:

- The release workflow runs only on pushes to `main`, `v*` tag pushes and manual runs, i.e. on
  code a maintainer merged or pushed. Its build job, which runs Gradle and so third-party code, has a
  read-only token and gets the signing secrets only in the two steps that need them; only the
  publish job can push.
- The release key only signs code that is on `main`: a manual run on another branch is debug-signed,
  and a tag that is not on `main` is refused.
- Every action is pinned to a full commit SHA with its version in a comment
  (`uses: owner/action@<40 hex digits> # vX.Y.Z`), because whoever controls an action's repository
  can move a tag like `v4` to other code. CI fails otherwise, and when a workflow has no
  `permissions:` block (`scripts/release/check-workflows.sh`). Dependabot
  ([`.github/dependabot.yml`](.github/dependabot.yml)) proposes the updates as `ci(deps):` pull
  requests, which don't publish a release. Review what changed in the action before merging one.
- All workflows have a read-only token, except the publish job. The job that signs doesn't use the
  Android SDK setup action or a Gradle cache written by another run.
- Pull requests from other repositories can't change the version.
- The workflow's own pushes (release commit and tag) use its token, which starts no workflow run, so
  a release can't trigger another one.
- Workflow inputs and event data reach scripts through environment variables, never through
  `${{ }}` inside `run:`.

## Signing

The release APKs are signed with the fork's key, kept only in the secrets
`RELEASE_KEYSTORE_BASE64` / `RELEASE_KEYSTORE_PASSWORD` (see the workflow). Every release must be
signed with that same key, or installed apps can't be updated.

- The SHA-256 digest of the key's certificate is in
  [`scripts/release/release-cert.sha256`](scripts/release/release-cert.sha256). After assembling,
  and again before publishing, `scripts/release/verify-apk-signer.sh` compares each APK's signer
  with it (`apksigner verify --print-certs`). **A release that is debug-signed or signed with any
  other key fails instead of being published**; so does one whose keystore secret is missing.
  Anyone can run the same check on a downloaded APK.
- Without the secrets (e.g. in a fork of this repository) a dry run's APKs are debug-signed, and a
  push to `main` there fails at the signing step: a fork that wants its own releases replaces the
  digest with its own key's.
- The job that signs runs in the `release`
  [environment](https://docs.github.com/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
  (dry runs away from `main` run in none). The secrets may be repository secrets or secrets of that
  environment; the workflow reads either.

Repository settings that go with this (they are not in the code, so check them after changing
anything here):

- *Environments → release*: deployment branches and tags limited to the branch `main` and the tags
  `v*`. **No required reviewers** and no wait timer, or releases stop being automatic (the signing
  job and the publish job would each wait for an approval).
- The signing secrets belong in that environment rather than at repository level: a repository
  secret can be read by a workflow run started from any branch by anyone with write access (who
  can edit the workflow on that branch), an environment secret only by runs on `main` and `v*`
  tags. To move them, add `RELEASE_KEYSTORE_BASE64` and `RELEASE_KEYSTORE_PASSWORD` to the
  environment with the same values, check with a dry run on `main`, then delete the repository
  secrets.
- *Rules → Rulesets*: a tag ruleset for `v*` that restricts creation, update and deletion, with
  the repository admin and **GitHub Actions** in the bypass list (the release workflow pushes the
  tag with its own token), and a branch ruleset or protection for `main`.
- *Actions → General*: workflow permissions "Read repository contents" (the default token is
  read-only), and optionally "Require actions to be pinned to a full-length commit SHA".

## Dependencies

- Libraries come from Google's Maven repository and Maven Central. [JitPack](https://jitpack.io),
  which builds artifacts from Git on demand, only serves the two groups that are published nowhere
  else (`com.github.bitfireat` for cert4android, `com.github.nextcloud` for Android-SingleSignOn;
  the content filter in [`settings.gradle.kts`](settings.gradle.kts)). cert4android is pinned by its
  full commit hash.
- **Every file Gradle downloads is checked against a SHA-256 checksum** recorded in
  [`gradle/verification-metadata.xml`](gradle/verification-metadata.xml): the plugins and what they
  depend on, the libraries, lint, aapt2 and each one's `.pom`/`.module` metadata, from all three
  repositories and for every flavor. A file with another checksum, or with none recorded, fails the
  build ("Dependency verification failed"), in CI and in the release build alike, before anything
  is signed. No repository or group is trusted as a whole. This matters most for JitPack, which
  can rebuild an artifact, so the bytes behind a version are not fixed there.
- The only exception: `-sources.jar` and `-javadoc.jar` files, which an IDE downloads for
  navigation, are not checked. They are never compiled, packaged or run.
- Signatures (PGP) are not checked: several artifacts are not signed at all (Material, older
  AndroidX libraries, both JitPack libraries), so they would need checksums anyway, and the rest
  would need a list of trusted keys that somebody reviews and keeps up to date, for little more
  than the checksums already give.
- Not covered, because Gradle doesn't download them: the Android SDK, a JDK that the toolchain
  resolver fetches when none is installed (CI installs its own), and the Android images that
  Robolectric downloads from Maven Central when the unit tests run.

### Changing a dependency

Any change to what the build downloads (a library, the Android Gradle plugin, a settings plugin, a
new Gradle task in CI that resolves something else) needs its checksums, or the build fails. In the
same pull request:

1. Change the version (`gradle/libs.versions.toml`); for cert4android or Android-SingleSignOn,
   review the new code first.
2. Run `scripts/dependencies/update-verification-metadata.sh` (a few minutes; it needs the Android
   SDK). It builds every variant, records what was downloaded, and adds aapt2 for the operating
   systems the build did not run on.
3. **Review the diff of `gradle/verification-metadata.xml`.** The script records whatever was
   downloaded, so this review is the check: only the components you changed, and what they newly
   pull in, should differ. It refuses to replace the checksum of a version that was already
   recorded; that means a repository now serves different bytes, so find out why.
4. Commit the file with the version change.

A pull request that changes a version without step 2 fails in CI with "Dependency verification
failed" and the list of files (sometimes below a "Configuration cache state could not be cached"
line); that includes one opened by a bot, which can't run the script.
Check out its branch, run the script, review and push the result to the same branch. (Dependabot
only updates the GitHub Actions here, which Gradle doesn't download, so today this only concerns
version changes made by hand.)

- The Gradle wrapper checks the Gradle distribution it downloads against `distributionSha256Sum` in
  [`gradle/wrapper/gradle-wrapper.properties`](gradle/wrapper/gradle-wrapper.properties). When
  updating Gradle, take the new checksum from <https://gradle.org/release-checksums/>
  (`./gradlew wrapper --gradle-version X.Y --gradle-distribution-sha256-sum <sum>`).

The application ID is `io.github.lazzurs.phonetrack` (`.dev` / `.play` for the other flavors),
different from the original app's `net.eneiluj.nextcloud.phonetrack`, so both can be installed
side by side. **Never change it again**: Android treats an app with another ID as a different app,
so existing installs would stop receiving updates.
